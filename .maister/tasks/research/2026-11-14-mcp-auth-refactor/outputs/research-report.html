MCP auth refactor: replacing token passthrough

TL;DR

Replace passthrough with RFC 8693 token exchange (delegation) at the existing hand-written host AS. The MCP server validates inbound tokens with RFC 7662 introspection (no cache) and checks that aud equals its RFC 9728 resource. It then exchanges the token for a short-lived backend token with aud = host API, client_id and act = MCP server, and scope = subject scopes ∩ user permissions. The host must issue aud (from RFC 8707 resource) on every token and reject tokens at /api/** whose aud is not the host API. No SAS or Keycloak migration now. Defer DPoP/mTLS and asymmetric keys: introspection means the MCP server never needs the host's signing key.

Key Decisions

  • Outbound: RFC 8693 token exchange, delegation. The only option that keeps the user's identity and permissions downstream and adds the MCP server as a distinguishable actor. Course M04L07, the team standard and six vendors use it.
  • Inbound: RFC 7662 introspection, no cache, plus an explicit aud check. No shared HMAC secret, immediate revocation, cheap on localhost.
  • Audience binding on both resource servers. Mandatory in every option; it closes replay in both directions.
  • Extend the custom AS. SAS exchange only accepts SAS-issued subject tokens, so migration is all or nothing.
  • Ship the scope ∩ permission intersection with the exchange grant. It closes the viewer→mcp:edit escalation.
  • Client credentials + propagated user header is rejected. It recreates the confused deputy.

Open Questions / Risks

  • warningOpen decisions: canonical aud values, default audience, principal propagation (threading), hand-written vs Spring exchange client, scope hierarchy, client seeding (D-1…D-13).
  • warningSpring defaults are unsafe here: an opaque principal is not an OAuth2Token; the interceptor reads an empty SecurityContextHolder on boundedElastic; the default cache is keyed by principal name, so scope leaks between clients.
  • criticalThree pre-existing AS-wide MUST violations remain unless follow-ups are bundled: token logging, refresh-token client binding, and the _token query parameter. Open DCR also stays (MAY in 2026-07-28).
  • warningThe PRM resource defaults to an external host. Once aud is enforced, a local run fails unless the default points at the local MCP URI.

Why not the others
  • A2b: the MCP server would hold the HS256 key used for every host token, so it could mint host tokens. Contradicts RFC 9068 J-02/J-13.
  • A4: the backend must trust the MCP server for user identity, which is the confused deputy. An unsigned header is forgeable by any holder of the client secret. It loses per-user consent and scope, and a signed-assertion variant reinvents exchange.
  • A5: high or very high one-off cost; SAS lacks native resource and does not intersect subject scopes; the MCP side is identical either way.
  • A6: the SHOULD-level gain is disproportionate for a localhost, plain-HTTP, server-to-server hop. Spring has no DPoP client.

Recommendation and target design

1. Audience everywhere

Host AS reads resource, issues aud, client_id, jti, typ at+jwt from a configured issuer. App tokens get aud = host API. Host filter requires iss + aud.

2. Inbound: introspection

opaqueToken() → /oauth2/introspect as the MCP confidential client. Require active and aud ∋ aj.mcp.base-url. Per-tool scope. 401/403 challenges. No cache.

3. Outbound: exchange

Per tool call: token-exchange grant, subject_token = validated T1, resource = host API. Send T2 only. No cache.

4. Exchange policy (AS)

Caller must own the MCP resource; subject aud = MCP URI; scope = T1 ∩ user perms ∩ client scopes; act = MCP server; exp ≤ min(5 min, T1 exp); no refresh token.

5. Keys

Keep HS256 for now: only the host verifies host tokens. Override the committed default secret (FU-5). JWKS later (FU-6).

Effort

Medium overall. Mostly host AS (grant, endpoint, claims, client auth). MCP side: deletions + Spring RS wiring + small exchange client.

How each brief vulnerability is eliminated

criticalToken passthrough

Root cause: JwtForwardingInterceptor re-sends T1; the host accepts it.

Fix: T1 only goes back to its issuer (introspection, exchange). The host receives T2 only. Interceptor, AccessTokenHolder and raw TOKEN_KEY are deleted, and the host would reject T1 anyway (aud ≠ host API).

Residual: none on this hop; a regression test asserts outbound header ≠ inbound token.

criticalConfused deputy

Root cause: the host cannot tell relayed calls from direct ones; the MCP server has no identity.

Fix: the MCP server authenticates as a confidential client; T2 carries client_id and act.sub; exchange is allowed only for MCP-audience subjects; scope is capped at user permissions.

Residual: matchers do not yet require act on mcp:* (optional, D-8).

criticalNo audience restriction / replay

Root cause: no aud on any token; the host checks none.

Fix: T0, T1 and T2 each get a distinct aud. MCP rejects T0 and T2; the host rejects T1. T2 lives ≤ 5 min.

Residual: bearer theft within audience and TTL (DPoP, FU-8).

criticalNo validation at MCP

Root cause: McpJwtFilter trusts any bearer; tools read the raw header.

Fix: Spring BearerTokenAuthenticationFilter + introspection + aud check before any tool runs. Tools see only the validated Authentication. Per-tool scope checks.

Residual: none; an introspection outage means 401 (fail closed).

Also resolved: V6 parsing split, V7 stale ThreadLocal, V8/V10 401/403 semantics. V9 external defaults is partly resolved (D-2).

Insights

Audience is the missing primitive High

Every brief vulnerability reduces to "no party knows whom a token is for". Exchange without a host-side aud check would leave the reverse path open.

Introspection decouples key management High

The MCP server never needs the HMAC key, so the asymmetric migration leaves the critical path.

Exchange is where escalation becomes systemic High

Copying subject scopes would mint backend write tokens for viewers. Intersect.

"Only exchange tokens issued to you" High

Tie the MCP server's client_id to the MCP resource URI (Auth0 and Keycloak precedent).

Threading dictates outbound wiring High

Spring defaults silently find no principal on boundedElastic.

Caching is a security decision here High

On a localhost hop the cost is two local calls per tool call; cache mistakes cause revocation lag and scope bleed.

Delegation is free Med-High

The AS already authenticates the actor, so act needs no actor_token.

Candidate standards

Metadata advertises only implemented behaviour (with a test per field). Every host JWT carries iss + aud and every RS checks both. Never log tokens, codes, verifiers or secrets.

SWOT (recommended approach)

Strengths

Meets every MCP-hop MUST; course- and standard-aligned; keeps users, permissions and filters; MCP side mostly deletions + Spring wiring; immediate revocation.

Weaknesses

More hand-written security code in the custom AS; two extra local calls per tool call; HS256 remains.

Opportunities

Fixes the viewer→mcp:edit escalation; clean path to JWKS/A2c, private_key_jwt, DPoP; act enables audit of MCP writes; good teaching artefact.

Threats

Spring defaults can reintroduce scope bleed; clients omitting resource get a defaulted aud; external default URLs break local aud checks; pre-existing AS MUST violations remain until follow-ups.

Conclusion

The aj MCP server should stop being a relay and become a proper OAuth resource server plus OAuth client. It accepts only tokens whose audience is itself, verified by introspection at the host AS. It authenticates to the AS as its own confidential client and exchanges the user's token (RFC 8693) for a short-lived token audience-restricted to the host API that carries the user as sub and the MCP server as act, with scopes no broader than the user's permissions. The host rejects any token whose audience is not the host API.

This meets MCP 2026-07-28 (MCP-07, -11, -29, -31), OAuth 2.1 §5.2/§7.1.4, RFC 9068 §4 claim validation, RFC 9700 §2.3 and RFC 8707, and it is the shape the course teaches in M04L07. Confidence: High for the direction, Med-High for Spring integration details.
