AcceptedADR-001: Validate-then-exchange replaces token passthrough

Overall direction · 2026-11-14 · Exploration: Problem Reframing
Context

The MCP server accepts any bearer (McpJwtFilter) and re-sends the client's token (JwtForwardingInterceptor + static AccessTokenHolder). The host accepts any token signed with its one HMAC key, and no token has an audience. MCP 2026-07-28 requires audience validation and forbids passthrough (MCP-07/-11/-29/-31), but leaves the mechanism open. RFC 8693 §1 describes this exact case.

Decision drivers
  • Every MUST on the hop
  • Per-user authorisation at the host (L04)
  • Relayed calls distinguishable (MCP-34)
  • L07 shape + team standard
  • Proportionate effort
Considered options
  1. A1 + A2a + A3: introspection inbound, RFC 8693 outbound, aud at both RS, extend the custom AS
  2. A4: client credentials + user header
  3. A2b/A2c: local JWT validation at the MCP server
  4. A5: migrate to SAS / Keycloak
  5. A6: DPoP/mTLS as the main fix
Chosen: option 1, because it alone meets every hop MUST, keeps the user's identity and permissions downstream, makes the MCP server a distinguishable actor and needs no key migration. It matches L07, the team standard and all vendor patterns found.
Good
  • Closes all four brief vulnerabilities
  • The MCP side is mostly deletions + Spring wiring
  • Tool behaviour unchanged
Bad
  • More hand-written AS security code
  • Two extra local calls per tool call
  • A4 rejected (confused deputy). A5 left to FU-9. A6 deferred (FU-8)

AcceptedADR-002: URI audiences with a lenient default

DA-1 → 1A · 2026-11-14 · Exploration: DA-1
Context

Audience is the missing primitive (I1). PRM resource, the RFC 8707 resource, T1 aud and the MCP check must be byte-identical (P-05, I8). J-08 requires a default when resource is omitted. J-16 requires distinct audiences. Claude's behaviour is unverified.

Decision drivers
  • One property drives PRM, challenge and aud check
  • Compatibility with clients that omit resource
  • AS identity ≠ API identity (J-16)
  • Works on a fresh clone
Considered options
  1. 1A URI audiences (aj.mcp.base-url, ${issuer}/api). Missing → MCP + WARN. Unknown → invalid_target
  2. 1B the same, strict
  3. 1C logical identifiers
  4. 1D host API audience = issuer
Chosen: 1A, because it is spec-native, preserves the PRM = aud invariant and does not break clients that omit resource. The default only ever yields an MCP-audience token. Exact match, no trailing slash. Defaults http://localhost:8081 and http://localhost:8080/api.
Good
  • One configured value per resource on each side
  • Misconfiguration fails loudly (invalid_target)
Bad
  • Implicit default for non-compliant clients (WARN)
  • No URI normalisation (stretch)
  • Tunnel deployments must align env on both apps

AcceptedADR-003: Host /api audience gate + per-grant resource policy

DA-2 → 2B · 2026-11-14 · Exploration: DA-2
Context

Without a host aud check, T1 could still be replayed at /api (I1, B-04, O-14). A resource registry knowing both URIs opens a new shortcut: /oauth2/authorize with resource = host API would bypass the MCP server.

Decision drivers
  • B-04/O-14 MUST
  • Close the auth-code→/api shortcut
  • No matcher changes
  • Generalises to future resources
Considered options
  1. 2A audience gate only
  2. 2B gate + per-grant resource policy (host-API audience only via exchange by the client bound to the subject's resource)
  3. 2C gate + actor requirement on mcp:*
  4. 2D 2B + 2C
Chosen: 2B, because it closes the shortcut at issuance with no matcher change. T0 gets aud = host API at login. The policy and binding are config-backed (ResourcePolicy), so there is no schema migration.

  • Replay closed both ways. /api accepts only T0 and T2
  • PERMISSION_mcp:* reachable only by T2

  • One more policy table. Future first-party clients need entries
  • Issuance is the single guard (2C stretch)
  • Legacy T0s rejected once

AcceptedADR-004: Hierarchical mcp:*, normalised at issuance, kept in T2, intersected at both grants

DA-3 → 3A · 2026-11-14 · Exploration: DA-3
Context

MCP-14 (new MUST) requires scope hierarchies. An mcp:edit-only token cannot GET today. Scopes are never intersected with permissions, so a viewer can get mcp:edit (F6). An exchange copying subject scopes would make that systemic (I3). The team standard says “map to READ/EDIT”, while the research lean was to keep mcp:* (K11).

Decision drivers
  • MCP-14 by behaviour
  • Close F6 at the source and at exchange
  • No matcher changes
  • T2 distinguishable from T0 (MCP-34)
Considered options
  1. 3A hierarchy expanded at the AS, T2 keeps mcp:*, ∩ permissions at both grants
  2. 3B independent, documented
  3. 3C translate to READ/EDIT in T2
  4. 3D hierarchy at the resource servers
Chosen: 3A, because the hierarchy lives in one function (ScopePolicy) and checks stay flat. Order: expand → ∩ permission scopes (READ↔mcp:read, EDIT↔mcp:edit) → ∩ client scopes → drop unknown. Empty → invalid_scope. Auth code uses consent-time permissions. Exchange uses current permissions.
Good
  • A viewer never holds mcp:edit (T1 or T2). Revocation applies on the next call
  • Edit-scoped clients can list
Bad
  • Issued scope can be wider than requested
  • Standard wording updated in the same change
  • Consent UI may still show mcp:edit to a viewer

AcceptedADR-005: Hand-written TokenExchangeClient; principal via McpTransportContext

DA-4 → 4A · 2026-11-14 · Exploration: DA-4
Context

Tools run on boundedElastic, so SecurityContextHolder is empty (F3). The static ThreadLocal is never cleared (V7). Spring's exchange provider + interceptor need three non-default overrides, any of which silently reintroduces a bug (K9).

Decision drivers
  • No static or thread-bound credentials
  • No hidden defaults or caches
  • Keep the SDK's async model
  • Outbound ≠ inbound must be testable
  • L07 names TokenExchangeClient
Considered options
  1. 4A hand-written client + Authentication in McpTransportContext, T2 passed explicitly
  2. 4B Spring provider + immediateExecution(true)
  3. 4C hybrid explicit provider
  4. 4D hand-written client + holder cleared in finally
Chosen: 4A, because it has the fewest moving parts and explicit data flow (T2 lives in the handler's stack frame). AccessTokenHolder, JwtForwardingInterceptor, McpJwtFilter and TOKEN_KEY are deleted. AjApiClient takes the bearer per call. A per-tool shortfall becomes McpToolException.insufficientScope before any exchange. HTTP 403 only for tokens with no mcp:* scope.
Good
  • No cross-thread or cross-user leaks
  • Outbound header directly assertable
  • No OAuth2 client starter
Bad
  • Hand-written OAuth client code
  • AjApiClient signatures change (tool contracts do not)
  • Relies on I5 (spike). Fallback 4D/4B
  • MCP-13 partly met for per-tool shortfalls

AcceptedADR-006: Introspection and exchange without caches; HS256 kept; T2 ≤ 5 min

DA-5 → 5A · 2026-11-14 · Exploration: DA-5
Context

Introspection decouples key management (I2): local validation would need the shared HMAC secret or a JWKS migration. On a localhost hop, caching is a security decision (I6). MCP is stateless. The team standard says no caching.

Decision drivers
  • The MCP server never holds a signing key (J-02/J-13)
  • Immediate revocation
  • No key infrastructure on the critical path
  • L07 + team standard
Considered options
  1. 5A introspection + exchange, no caches, HS256
  2. 5B short-TTL caches keyed by SHA-256(T1) + client_id
  3. 5C local JWT + RS256/JWKS now
Chosen: 5A. POST /oauth2/introspect requires caller auth and returns {active:false} (no detail) for any unusable token, including tokens whose aud is not the caller's bound resource. The MCP server also checks aud itself. T2 exp = min(now + 5 min, T1 exp). The response carries expires_in and issued_token_type.
Good
  • Revocation and permission loss apply on the next call
  • Nothing to invalidate
  • JWKS (FU-6) remains a clean upgrade
Bad
  • Two local calls per tool call (unmeasured)
  • Host outage → rejected (fail closed)
  • HS256 remains

AcceptedADR-007: Implicit delegation via act

DA-6 → 6A · 2026-11-14 · Exploration: DA-6
Context

The brief's confused deputy is the accountability gap: the backend cannot tell relayed calls from direct ones (MCP-34). The MCP server authenticates at the exchange, so the AS already knows the actor (I7).

Decision drivers
  • Auditable accountability (X-15)
  • No extra client machinery
  • Auth0 OBO / SAS alignment
Considered options
  1. 6A AS adds act: {sub: <mcp client_id>}, no actor_token
  2. 6B impersonation (client_id only)
  3. 6C actor_token from a new client_credentials grant
Chosen: 6A, because it gives the standard delegation claim at zero client cost. T2: sub = user, client_id = act.sub = aj-mcp-server.
Good
  • The host can audit or later enforce (2C)
  • No client_credentials grant needed
Bad
  • Actor asserted by client auth, not a token. Multi-hop would need 6C
  • act not yet required for mcp:*

AcceptedADR-008: One ClientAuthenticator; env-driven startup upsert of the MCP client

DA-7 → 7A · 2026-11-14 · Exploration: DA-7
Context

Introspection needs an authenticated caller (I-03), and exchange must be restricted to the client bound to the MCP resource (I4). Client auth is inline today, reads only client_secret, and ignores the advertised Basic method (F5, P8). No confidential client exists. The committed JWT secret default shows how secrets drift into the repo (F7).

Decision drivers
  • Honour Basic, keep post
  • No committed secret or hash
  • Every Liquibase context
  • One client registry
  • Fresh clone works via start-dev
Considered options
  1. 7A ClientAuthenticator (Basic + post, BCrypt) + McpClientProvisioner upsert from AJ_OAUTH_CLIENT_ID/SECRET
  2. 7B Liquibase dev changeset with a known hash
  3. 7C config-defined internal clients
Chosen: 7A. Client: grant token-exchange, Basic + post, scopes mcp:read mcp:edit. Resource binding via app.oauth2.mcp-client-id in ResourcePolicy (no schema change). Missing env: the host skips with a WARN and keeps serving (introspect/exchange → invalid_client). The MCP server fails fast. start-dev exports the same values to both apps. Both credential methods at once → invalid_request.
Good
  • Fixes advertised-but-ignored Basic (P8)
  • Rotation = change env + restart
Bad
  • Startup writer with side effects (idempotency tests)
  • Theoretical DCR id collision
  • private_key_jwt waits for FU-6/7

AcceptedADR-009: Bundle same-touch hygiene: FU-3, FU-5, FU-2a

DA-8 → 8B · 2026-11-14 · Exploration: DA-8
Context

Pre-existing MUST violations remain after the hop fix. B-12: token logging. B-15/O-07: unbound refresh tokens. O-09: _token. External kuba-* defaults break the local aud check. Several sit in code this change rewrites.

Decision drivers
  • Don't touch the same lines twice
  • Consistency within a file
  • No AS-wide sweep
Considered options
  1. 8A hop only
  2. 8B + FU-3 (no secret logging), FU-5 (local defaults, env wiring incl. APP_JWT_SECRET, CORS env), FU-2a (refresh bound to client + resource)
  3. 8C + FU-4 _token
  4. 8D full sweep
Chosen: 8B, because each item edits a structure the hop already changes, closing B-12 and half of B-15/O-07 almost for free. FU-4 stays a stretch (the consent page depends on it). FU-2b needs its own storage decision.
Good
  • No secrets in AS logs (log-capture test)
  • Fresh clone works. Tunnels configure via env
Bad
  • Larger diff, more tests
  • Debug habits relying on old logs break
  • Committed JWT secret default remains. O-09 open until FU-4
