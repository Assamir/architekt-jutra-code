Validate-then-exchangearchitecture style

TL;DR

  • The MCP server becomes a real OAuth resource server and OAuth client. It accepts only tokens whose aud is its own URL (checked via RFC 7662 introspection at the host, no cache). For every tool call it exchanges the user's token (RFC 8693) for a ≤ 5 min token with aud = host API, act = MCP server and scopes ∩ the user's current permissions. The client's token never reaches /api.
  • The host gets one configured issuer, an aud on every token, and an aud + iss gate on /api. A per-grant resource policy means only the token-exchange grant, called by the MCP confidential client, can mint a host-API token.
  • P1 = 1A, 2B, 3A, 4A, 5A, 6A, 7A, 8B. Tool names, inputs and outputs stay the same (course L07). No schema migration. Both apps ship together.

Key Decisions

  • Validate-then-exchange replaces passthrough (ADR-001).
  • URI audiences: MCP = aj.mcp.base-url, host API = ${issuer}/api. A missing resource defaults to the MCP URI with a warning. An unknown one gets invalid_target (ADR-002).
  • /api requires iss + aud = host API. Only the exchange grant may mint that audience (ADR-003).
  • mcp:edit ⊃ mcp:read, normalised at issuance and kept in T2. Scopes ∩ permissions at both grants (ADR-004).
  • A hand-written TokenExchangeClient. The Authentication travels in McpTransportContext, and the ThreadLocal is deleted (ADR-005).
  • Introspection and exchange with no cache, HS256 kept (ADR-006). Implicit act (ADR-007).
  • ClientAuthenticator + env-upserted aj-mcp-server (ADR-008). FU-3, FU-5 and FU-2a bundled (ADR-009).

Open Questions / Risks

  • warningThe resource value Claude sends is unverified. Exact match only, so a trailing slash causes invalid_target.
  • warningThe contextExtractor must see the post-filter SecurityContext on the servlet thread. Spike it first. Fallback: immediateExecution(true).
  • infoMCP-13 is only partly met: HTTP 403 only for tokens with no mcp:* scope. A per-tool shortfall is a tool error.
  • infoThe issued scope can be wider than requested. Client handling is unverified.
  • infoTwo extra local HTTP calls per tool call (unmeasured).
  • infoExisting T0/T1 have no aud, so users re-login and Claude re-authorises once.
  • infoThe committed APP_JWT_SECRET default stays as a fallback. start-dev overrides it.

Design Overview

Business context

The MCP server is a trust-and-forward relay: it accepts any bearer and re-sends it, and the host accepts any token signed with its one HMAC key. MCP 2026-07-28 forbids this (MCP-07/-11/-29/-31). The repo is also the course's M04 baseline (bd4de70). Beneficiaries: end users, course students, developers on start-dev.

Chosen approach

Validate-then-exchange (delegation) on the existing custom AS: introspection + audience check inbound, a confidential client doing RFC 8693 per tool call, a host-API-audience T2 with act. The host binds every token to an audience and gates /api. Style unchanged: a modular-monolith host with an embedded AS, plus a separate stateless MCP resource server.

Principles

  • One audience per token, and every RS rejects tokens minted for someone else.
  • The MCP server never holds a key and never forwards inbound tokens.
  • T2 scopes ≤ the user's current permissions.
  • No caches, framework defaults, key migration or schema migration.

Data Flow

  1. Entry: JSON-RPC with Bearer T1 to the MCP server. The SPA and plugins use T0 (unchanged).
  2. Inbound validation: introspect T1 (Basic), require active + aud ∋ aj.mcp.base-url, build a BearerTokenAuthentication with SCOPE_mcp:*. No cache.
  3. Principal hand-off: on the servlet thread the extractor copies the Authentication into the immutable McpTransportContext. There is no static or thread-bound state.
  4. Per-tool authorisation: mcp:read for list tools, mcp:edit for aj_add_product. A failure becomes a tool error before any outbound call.
  5. Exchange: the AS validates T1 against the caller's bound resource, recomputes scopes from current permissions and mints T2. T2 lives only in the handler's stack frame.
  6. Downstream: AjApiClient sends Bearer T2. The API gate checks iss + aud. The unchanged matchers authorise.
  7. Exit: the unchanged CallToolResult. Errors map to McpToolException.

Stored state: only the upserted client row is new. In-memory codes and RTs gain resource (+ client_id). Neither app persists T1 or T2.

How Each Vulnerability Is Eliminated

passthrough

Cause: JwtForwardingInterceptor re-sends T1.

Fix: interceptor, holder and TOKEN_KEY deleted. The only outbound bearer is T2. T1 at /api → 401.

Test

outbound header == T2 ≠ T1. T1 at /api → 401

Residual

none on this hop
confused deputy

Cause: the host cannot tell relayed from direct calls, and the MCP server has no identity.

Fix: confidential client. T2 client_id + act. Exchange only for the caller's bound resource. Scopes ≤ current permissions. Only exchange mints the host-API audience.

Test

viewer ≠ mcp:edit. Non-MCP exchange rejected. resource=API → invalid_target

Residual

matchers do not require act (2C deferred)
no audience / replay

Cause: no aud anywhere.

Fix: T0/T1/T2 each have one distinct aud, and both RS enforce theirs. T2 ≤ 5 min.

Test

T1→/api 401. T0/T2→MCP 401. T2 as subject rejected

Residual

theft within audience + TTL (DPoP = FU-8)
no MCP validation

Cause: McpJwtFilter trusts any bearer.

Fix: resource-server chain + introspection + aud before dispatch. Per-tool scope.

Test

no / garbage / expired / foreign token → 401. Read token on add → scope error, no backend call

Residual

outage = rejected (fail closed)

Concrete Examples

1. Editor lists products

Given

editor (READ, EDIT) holds T1 {aud MCP, [mcp:read, mcp:edit]}

When

Claude calls aj_list_products(search="mug")

Then

Introspect OK, then mcp:read passes, then T2 {aud …/api, act, ≤ 5 min}, then GET /api/products?search=mug with T2 only. Same {"products": [...]} as before.

2. Viewer cannot escalate

Given

viewer (READ) consents to scope=mcp:edit

When

T1 is issued

Then

Issued scope = mcp:read. aj_add_product → “Insufficient scope: requires mcp:edit”, no exchange. If READ is revoked later, the next exchange fails with invalid_scope (“Insufficient permissions”).

3. Stolen T1 replayed at host

Given

An attacker holds a valid T1

When

GET /api/products with it

Then

401 (aud ≠ host API). Authorize with resource=API → invalid_target. Exchange without the MCP secret → invalid_client.

4. Misconfigured tunnel

Given

The MCP server has AJ_MCP_BASE_URL=https://mcp.example.test, the host still has the default

When

Claude authorises with that resource

Then

invalid_target plus one WARN naming the unknown resource, instead of silent 401s.

Test Strategy (outline)

Host (integration, TestContainers, MockMvc)

  • /api gate: T0 200. T1 replay 401. Wrong iss 401. No aud 401. T2 GET 200. T2 read-only POST 403
  • Resource policy: default MCP, unknown → invalid_target, host API on code/refresh → invalid_target
  • Scopes: editor edit → read+edit. Viewer never gets mcp:edit (code + exchange). Revoked → invalid_scope
  • Exchange: claims, TTL, issued_token_type, no RT. Non-MCP client rejected. T0/T2 subject rejected. Bad resource
  • Client auth: Basic, post, both, wrong secret. Introspection: unauth 401, active vs inactive
  • Refresh by a different client → invalid_grant. Provisioner idempotent / skip. Metadata fields
  • Log capture: no token, code or secret in logs. Rename the misnamed tokenExchange_* tests

MCP server (spring-security-test, mock host)

  • Delete McpJwtFilterTests, AccessTokenHolderTests. Rewrite RestClientConfigTests
  • Chain: 401 (no error), 401 invalid_token (inactive, foreign aud), 403 insufficient_scope, outage not invalid_token
  • Spike first: Authentication reaches the handler via McpTransportContext
  • Outbound header == T2 ≠ T1. One exchange per call. Scope shortfall → zero outbound. Exchange failure → apiError. Backend 401 no retry. Concurrent calls isolated
  • Tool schemas and outputs unchanged. PRM defaults. Fail fast without secret

Manual rollout gate

start-dev + MCP Inspector or Claude: discovery, then DCR, consent and the three tools behave as before. Viewer add is refused. Record what resource the client sends.

Migration and Rollout

  1. One PR, both apps. Neither half works alone.
  2. Order: properties/issuer/claims, then policies + authenticator + authorize/token + FU-3, then the API gate, then provisioner/introspection/exchange/metadata, then the MCP chain + spike, then exchange client + rewiring + deletions, then tests, then start-dev + docs.
  3. Expected session invalidation: old T0s get 401 and the SPA redirects to login. Old T1s get 401 invalid_token and Claude re-authorises. RTs are in memory anyway.
  4. Tunnel deployment: set APP_OAUTH2_ISSUER, AJ_MCP_BASE_URL, AJ_OAUTH_SERVER_URL and AJ_OAUTH_CLIENT_ID/SECRET consistently. The kuba-* defaults are gone.
  5. Exercise baseline bd4de70: the six passthrough-pinning test classes are rewritten or deleted. The commit says this is the L07 target.
  6. Rollback: revert the PR. No schema migration. The client row is inert.
  7. Docs and standards land in the same PR.

Out of Scope

  • Stretch: 2C actor requirement. URI normalisation. FU-4 _token. HTTP 403 step-up per tool.
  • Deferred: FU-1 DCR→CIMD. FU-2b RT persistence/reuse detection. FU-6 JWKS. FU-7 private_key_jwt. FU-8 DPoP/mTLS. FU-9 SAS. FU-10 CIMD/ID-JAG. FU-11 misc hardening.
  • Removing the committed APP_JWT_SECRET default. Caching, latency metrics, act-keyed audit log, PRM resource_name.
  • Frontend/consent UI (may still list mcp:edit for a viewer, but the token will not contain it).
  • New candidate standards are suggested to the user per CLAUDE.md, not applied. Only existing wrong standards are corrected.

Success Criteria

  1. No passthrough: outbound Authorization never equals the inbound token (automated, all tools).
  2. Audience isolation: T1 → /api 401. T0/T2 → MCP 401. Auth-code request for the API audience → invalid_target.
  3. Least privilege: no grant yields scope beyond current permissions. Viewer tests pass at both grants.
  4. Compliance: every hop MUST in research-report §5 Met. B-12 Met. Client-binding half of B-15/O-07 Met.
  5. Unchanged tools: identical names, schemas and outputs. The L07 manual run works on a fresh clone with no manual env.
  6. Freshness: revocation, expiry and permission loss apply on the next tool call. T2 ≤ 5 min and ≤ T1 exp.
