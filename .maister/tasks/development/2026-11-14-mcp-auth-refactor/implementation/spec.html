TL;DR

  • The MCP server stops forwarding the client's token. It validates every bearer token through RFC 7662 introspection at the host and checks aud itself. For each tool call it exchanges the token (RFC 8693) for a short-lived host-API token (T2) and calls /api with T2 only.
  • The hand-written host AS gets a fixed issuer, an aud on every JWT, RFC 8707 resource handling (slash-equal origin URIs), ScopePolicy (expand ∩ permissions ∩ client scopes, re-expand), ClientAuthenticator, an introspection endpoint, an exchange grant and an env-provisioned aj-mcp-server client. /api accepts only iss = issuer and aud ∋ ${issuer}/api.
  • Ports move to host 8180, MCP 8181, MCP management 9181. Same-touch hygiene: no token logging in either app (FU-3), local defaults and env wiring (FU-5), refresh tokens bound to their client (FU-2a). Three small consent/SPA touches. Tool names, schemas and results do not change.
  • Revised after the spec audit (3 major, 15 minor, 4 user decisions): timed introspection client, byte-identical red tests, stricter error codes and test-plan gaps closed — see Audit resolution.

Goal and Scope

Eliminate token passthrough, confused-deputy and audience-replay vulnerabilities on the MCP → host hop by making every token audience-bound and having the MCP server validate inbound tokens and use delegated, short-lived host tokens. The goal includes making the four Phase-3 red tests pass and leaving MCP tool behaviour unchanged for users.

In scope

  • Host AS: fixed issuer, resource/aud, ScopePolicy, ClientAuthenticator, exchange grant, introspection, provisioner, typed errors, metadata
  • Host /api iss + aud gate; session-only consent principal
  • MCP: resource-server chain, audience check, challenges, context hand-off, ToolSecurity, TokenExchangeClient, explicit T2, deletions
  • Frontend: hidden resource, grantable scopes on consent, drop stored T0 without aud, Vite proxy port
  • Ports 8180 / 8181 / 9181, start-dev env wiring, CORS env override
  • FU-3 (no secret logging), FU-5 (local defaults), FU-2a (refresh client binding)
  • CLAUDE.md, standards, project and plugin docs rewritten to match code

Out of scope

  • DCR → CIMD / pre-registration (FU-1); the DCR grant_types null path and redirect validation were fixed during verification (AS-17)
  • Refresh-token persistence, reuse detection, absolute lifetime (FU-2b)
  • JWKS / asymmetric keys (FU-6), private_key_jwt (FU-7), DPoP/mTLS (FU-8), SAS/Keycloak (FU-9), CIMD/ID-JAG (FU-10)
  • _token restriction (FU-4); 2C actor requirement
  • Introspection or exchange caching, latency metrics, audit on act.sub
  • Per-tool HTTP 403 step-up, redirect-style authorize errors, state encoding and other FU-11 hardening
  • Removing the committed APP_JWT_SECRET fallback; Vite proxying of /oauth2/*
  • plugins/*/dist/, .playwright-mcp logs, week7/–week10/, tools/, _docs/
  • New candidate standards (suggested to the user only)

User Stories

Editor using ClaudeWants aj_list_products, aj_list_categories and aj_add_product to work exactly as before, so that the security change is invisible.
ViewerWants the consent page to offer only what they can grant (mcp:read), so that they are not misled. aj_add_product is refused with a clear tool error.
aj userWants a token stolen from Claude (T1) to be useless at the host API, so that their authority cannot be replayed or escalated.
DeveloperWants start-dev to wire both apps on 8180/8181 with matching credentials, so that a fresh clone works without manual env setup.

Technical Approach

Flows, filter order, migration and implementation order
  • Host flow: login mints T0 (aud = API) → consent POST runs ResourcePolicy, the session check and ScopePolicy → code {grant, resource} → token issues T1 (aud = MCP) + RT {client, resource} → MCP introspects and exchanges → the /api gate accepts T0/T2 only.
  • Filter order: JwtAuthenticationFilter (API mode, _token too) → Registration → Authorization → Token (code / refresh / exchange) → Introspection. The filters stay non-beans, so ApiLayerTests is unaffected.
  • MCP flow: BearerTokenAuthenticationFilter → AudienceValidatingIntrospector → SCOPE_mcp:* → / authorisation → contextExtractor → handler (boundedElastic) → ToolSecurity → TokenExchangeClient → AjApiClient with T2. No ThreadLocal, no static state, no caches.
  • Migration: no DB migration (client row in oauth2_registered_client; grant types stored as raw strings). Both apps ship together. Rollback = revert.
  • Order: (0) commit both red-test files unchanged as the baseline (RG-1) → (1) properties, claims, port config → (2) policies, authenticator, writer, authorize/token, FU-3 → (3) API gate → (4) provisioner, introspection, exchange, metadata → (5) MCP chain + context hand-off (red tests 3/4 first) → (6) exchange client, services, deletions → (7) tests → (8) frontend, start-dev, docs.
