TL;DR

New iframe plugin plugins/shipping (Vite + React, port 3010, strictPort). Carriers and delivery methods are stored as plugin objects keyed by PluginObject.objectId (a UUID). Each product's opt-outs go in pluginData {disabledMethodIds}, so the backend does not change.

A sidebar "Shipping" page manages carriers and methods: add, edit inline with the same id, toggle active, delete. A product "Shipping" tab lets editors untick methods, warned by a rotation-aware size check against box-size dimensions. The tab reloads box and method data on focus and keeps unsaved ticks.

The only host code change is truck: Truck in ICON_MAP, with a Vitest test. It must add no lint problems to the existing baseline of 16. Six docs record the port rule: 3004–3009 for demo and utility plugins, 3010 and up for business modules.

Open Questions / Risks

  • warningManifest registration is manual (admin token). Size warnings work only when box-size is registered under the id box-size.
  • warningReload-on-focus trigger: host tab iframes stay mounted and are switched with display, so switching tabs probably fires neither focus nor visibilitychange in the iframe. The refresh then runs on the first click inside the tab, or when the browser tab becomes visible again. Unsaved ticks are kept. Check this in the walkthrough.
  • infoConcurrent editors can overwrite each other (full-replace saves, no versioning). This is acceptable at this scale.
  • infoError messages are terse (empty statusText). A contextual prefix is shown, e.g. "Failed to save: 403".
  • infoFollow-ups: restriction visibility on the product list or detail info, MCP exposure, checkout consumers, and the ../../sdk page import path in plugins/CLAUDE.md.
  • infoResolved: H1, M1–M3 and L1–L8. See Audit Resolution.

Goal & Scope

Let editors maintain a system-wide catalogue of carriers and delivery methods, and turn individual methods off per product, warned when the product's box exceeds a method's size limits, all as an isolated plugin on port 3010.

In scope

  • The plugins/shipping app (scaffold, manifest, domain, 2 pages)
  • Carrier and method CRUD with inline edit (same objectId), active toggles, blocked carrier delete
  • Product tab: availability checkboxes, size-check badges, warning hint, save / remove data, reload on focus
  • Permission gating (EDIT) and read-only variants
  • Host ICON_MAP truck entry and its Vitest test
  • Plugin Vitest tests for domain helpers (16 tests)
  • Docs: plugin-development.md, INDEX.md, tech-stack.md, plugins/CLAUDE.md, CLAUDE.md, README.md

Out of scope

  • Backend, schema, security, SDK (incl. the PluginObject.id type) or plugin-ui.css changes
  • Weight limits; seed or default carriers
  • Restriction visibility outside the product tab; MCP tools; checkout or order consumers
  • Auto-disabling by size; bulk per-product operations; cascade carrier delete; delete confirmations
  • Host-side cross-plugin notifications or an iframe reload on tab switch
  • A general resolveIcon fix; pre-existing host lint problems; the plugins/CLAUDE.md sdk import path fix

User Stories

Editor: add carriers (DHL, DPD, InPost, Poczta Polska…) and methods with optional max L×W×H, so the system knows which shipping options exist.
Editor: rename carriers and edit a method's carrier, name and limits in place, so typos and limit changes don't wipe product restrictions.
Editor: deactivate a carrier or method without deleting it, to suspend it and keep per-product settings.
Editor: untick methods on a product's Shipping tab and see which ones its box is too large for, so unsuitable methods are not offered.
Viewer: see carriers, methods and per-product availability read-only, without being able to change them.

Requirements

Sorting rule (reqs 1, 6, 16, 19): carriers sort by name; methods sort by carrier display name, then method name. All comparisons are case-insensitive. A missing carrier sorts as "Unknown carrier". Mockup row order does not override this rule.

Technical Approach

EntityStorageDomain idShape
Carrierobjects carrierPluginObject.objectId (UUID){name, active}
Delivery methodobjects shipping-methodPluginObject.objectId (UUID){carrierId, name, active, maxLengthCm?, maxWidthCm?, maxHeightCm?}
Product restrictionplugin_data.shipping(product id){disabledMethodIds: string[]}

PluginObject.id is the numeric DB key and is never used as a domain id. Using it would create duplicates on edit, make deletes return 404, and corrupt opt-outs.

Flow, fit check and runtime rules
  • Flow: the iframe calls the SDK, which sends a postMessage to PluginMessageHandler. The handler checks the exact origin http://localhost:3010 and calls the REST API with the user's JWT. READ is required on GETs and EDIT on writes.
  • Writes: objects.save(type, objectId, fullData), then both lists reload. Edits and toggles reuse the objectId.
  • Fit check: sort the box dimensions in descending order. Replace each missing limit with +∞, then sort the limits in descending order. The box fits when each box dimension is ≤ the limit at the same position. With all three limits missing, the result is "no-limits". Example: box (120, 48, 12) vs limits (64, 41, 38) gives too-large; vs (∞, ∞, 130) it fits.
  • Effective active: method.active && carrier?.active === true.
  • Product tab state: the selection is set from stored data on the initial load and after Save, and otherwise changes only through checkbox toggles. Refreshes replace the product, carrier and method data, never the selection.
  • Async rules: Promise.all for loads, void-wrapped handlers and listeners, no as unknown as casts.
  • Pitfalls: productId arrives as a number; avoid /detail and /edit paths; errors are status text only (often empty); a 401 redirects the host; deleting a missing object returns 404; tab iframes stay mounted, so the tab refreshes itself.
  • Registration: PUT /api/plugins/shipping/manifest with a PERMISSION_PLUGIN_MANAGEMENT token (documented).

Success Criteria

  • The plugin's npm run build (tsc -b incl. the test file) and npm test (16 tests) pass. The host icon test (3) passes. There are no new lint problems against the baseline of 16 problems (14 errors), and Icons.tsx:26:17 is pre-existing.
  • The plugin is served on :3010, and a second instance fails because of strictPort. The sidebar shows "Shipping" with the Truck icon, and products show a Shipping tab.
  • Editor: CRUD with the objectId unchanged on edit and no duplicates; one edit row at a time; blocked carrier delete with the singular or plural message.
  • Editor: with box 120×12×48 and both InPost methods ticked, Kurier (80×50×35) and Paczkomat (64×38×41) are "Too large", Kurier sorts first, and the plural hint names both. Unticking one leaves the singular hint.
  • Editor: an unticked method persists after reload, stored as objectIds, and "Saved!" shows for 2 s. Ticking everything removes the data.
  • Editor: editing or renaming a disabled method keeps it disabled. Deactivating it shows "Inactive" with the opt-out preserved, and reactivating re-applies it.
  • Editor: after a Box Size edit, returning to and focusing the Shipping tab updates the box line and badges, and unsaved ticks are kept.
  • Viewer: no write controls, disabled checkboxes, and the read-only notices are shown (except in the product-tab empty state).
  • All 8 screens and 2 components match their mockups in layout, components and states. Where a mockup's sample data or wording conflicts with a spec rule, the rule wins.
  • All six docs reflect shipping on 3010 and the port rule: 3004–3009 for demo and utility plugins, 3010+ for business modules (next 3011).
