TL;DR

  • New iframe plugin plugins/ai-offer-analysis (port 3011) clones the ai-description stack (Next.js 15 Pages Router, BAML pinned 0.220.0, Jest); one BAML function AnalyzeOffer goes through LiteLLM (gpt-4o-mini) and returns typed verdicts on description quality, category fit and price vs market.
  • Plugin code adds peer price stats from the product's assigned category (self excluded), the deviation %, category validation and the needsReview rule.
  • Each result is stored as a bound plugin object plus a compact setData summary that drives the info badge and the native "AI: needs review" list filter.
  • For editors the tab auto-runs only once its iframe is actually visible (the host mounts hidden tab iframes on page load), only when the analysis is missing or its fingerprint changed, and never repeats a failed auto-run in the same session.
  • Done means a live run is counted and attributed to ai-offer-analysis in the LiteLLM logs with an executable baseline/delta procedure.
  • Phase 11 fix cycle 1 changed parts of this contract (pricedAs, a peer-contamination guard with marketRangeUnreliable, a narrower CONTENT_BLOCKED, sanitized failure logging, BAML_LOG=warn, the LiteLLM upstream mapping). See Spec deviations; the code is the reference for them.

Key Decisions

  • Stack: clone ai-description without its defects. @boundaryml/baml is pinned to exactly 0.220.0, and Jest runs via node node_modules/jest/bin/jest.js, which works on Windows.
  • Staleness: decided by a deterministic content fingerprint, not by updatedAt. updatedAt is the @Version column and every setData bumps it, which would cause a re-analysis loop.
  • Fingerprint: cyrb53 over a canonical JSON array, written as 14 hex characters. It is synchronous, has no dependencies and gives identical output in the browser and in Node/Jest. Web Crypto SHA-256 was rejected because it is async and its Jest/Node availability is uncertain.
  • Verdicts from the LLM, decisions in code: the deviation %, peer stats, suggested-category validation and the needsReview rule (POOR, or MISMATCH, or ABOVE/BELOW with |dev| ≥ 30%) are all computed in code. Code also forces the price confidence to LOW and drops the deviation when the market range looks copied from wrong-category peers (amended — see Spec deviations).
  • EDIT gate before any host or LLM call: the route decodes the JWT with shipping's base64url-safe canEdit and returns 403 without EDIT. The host then rejects forged tokens on getProduct.
  • One BAML client: no fallback wrapper and no retry policy, so there is exactly one LiteLLM log entry per analysis. base_url is hardcoded to http://localhost:4000/v1.
  • Static attribution: user "ai-offer-analysis" plus metadata (tags, trace_name, generation_name). The audit confirmed offline that BAML 0.220.0 puts them in the request body; the x-litellm-tags header stays as the fallback.
  • Timeout: AbortSignal.timeout(45000) passed in the BAML call options (signal).
  • Auto-run only when the tab is visible: the saved analysis loads at mount (cheap host GETs), but the auto-run waits for a non-zero iframe viewport (window resize when hidden). One auto-run attempt per iframe session; Retry/Re-analyze are manual.
  • Peers from the assigned category: always, self excluded with String(p.id) === String(product.id). The prompt tells the LLM to ignore peers of a different product type, so a mis-categorized product's price verdict comes from the market estimate. The prompt now also forbids deriving the range from peers (amended — see Spec deviations).
  • Registration: a 013 Liquibase dev seed with the plugin row and two fictional, flawed demo products (AOA-DEMO-*). ON CONFLICT DO NOTHING; demo products inner-join their category so a missing category skips the row. Curl is the alternative and the way to re-register after manifest changes.
  • UI: the mockups are binding. Neutral verdicts use a plain tc-badge. Compact layout for GOOD/FITS/FAIR sections, detailed otherwise. Re-analyze disabled while running. A native <progress> replaces the mockup's CSS spinner. Numbers use en-US with 2 decimals; mockup grouping and peer numbers are illustrative.

Open Questions / Risks

  • warningLiteLLM request_tags recording. BAML sends body metadata.tags and user (verified offline); whether LiteLLM main-stable stores them as request_tags/end_user is only known at live verification. If not, switch to the x-litellm-tags header and record which worked.
  • warningPresidio masking (PHONE, PESEL \b\d{11}\b) can mangle digit runs. Prices are sent as USD 1799.99 and SKUs are not sent. Inspect the logged prompt (amended — see Spec deviations): prompts are in the LiteLLM spend logs and Langfuse, not in the plugin log.
  • infoLLM nondeterminism: price and category verdicts can flip, and a fictional brand may still yield INSUFFICIENT_DATA. Mitigations: temperature 0.1, the deterministic rule, the plain badge for uncertain verdicts, prompt wording for unknown brands, and demo expectations that need only one strongly cued flag per product.
  • infoVisibility gate depends on browser behaviour: a display:none iframe must report a 0×0 viewport and fire resize when shown (Chromium and Firefox do). Verification step 1 checks it.

Goal & Scope

Deliver a plugin on port 3011 that uses BAML structured output, with all traffic routed through LiteLLM. When an editor opens the product tab, it automatically assesses an offer's description quality, category fit and price against market norms. The result is persisted and surfaced in the tab, the info badge and the native list filter, and the LiteLLM traffic is verifiably logged.

In scope

  • The new plugin plugins/ai-offer-analysis: BAML, API route, tab, badge, manifest
  • The 013 Liquibase dev seed: plugin row and 2 flawed demo products
  • Jest tests (domain and route); the host suite stays green
  • Docs: plugin README and the port, plugin and env lists
  • Live LiteLLM / spend logs / Langfuse verification

Out of scope

  • Host Java or host frontend changes, and new host event types
  • A bulk or "analyze all" page, and a menu.main entry
  • Fixing the server-sdk.ts 204 bug or ai-description's defects
  • Per-user LiteLLM metadata, virtual keys, LiteLLM or Presidio config changes (amended — see Spec deviations): the user approved the gpt-4o-mini upstream mapping change
  • Currencies other than USD, and external price APIs
  • UI component tests for the Next.js pages, and deleting analyses or cleaning up on product delete
  • Re-analysis triggered by other categories or peer prices changing (known limitation; Re-analyze covers it)

User Stories

EditorWhen I open the "AI Offer Analysis" tab, I want the analysis to run on its own if the product is new to the analysis or has changed, so I see current verdicts without clicking anything else. Merely visiting a product page without opening the tab spends no LLM tokens.
EditorIf an automatic run fails, I want it not to retry by itself, so a persistent gateway problem does not keep spending calls; I retry with the Retry button.
EditorI want a Re-analyze button, so I can refresh the verdicts after editing a product.
ViewerI want to see the last saved analysis and know whether it is out of date, without being able to spend LLM tokens.
Catalog managerI want an "AI: needs review" switch on the product list, so I can find every flagged offer at once.
Any userI want a one-line AI review badge under the product details, so I can see the verdict without opening the tab. Until an editor has opened the tab, it says "not analyzed yet".
Course participant / operatorI want every model call to be visible and attributable in LiteLLM and Langfuse, so I can confirm all traffic goes through the gateway.

Prompt outline (says "product" throughout):

  1. Role: catalog quality analyst. All prices are in USD; never invent specs.
  2. Product block.
  3. Description criteria and verdict.
  4. Category fit against the full list (name: description). The suggestion must be copied exactly from the list, or be null.
  5. Price: typical US retail range for this product or comparable products of the same type and specs (unknown brand → estimate from comparables, LOW confidence, not INSUFFICIENT_DATA); peer stats plus up to 10 peer lines from the assigned category, which may be a different product type and must then be ignored; or "No other catalog products in this category." (amended — see Spec deviations): the type is identified first (pricedAs), the range must not be derived from peer prices, and peers come after the range instruction as "Catalog context".
  6. {{ ctx.output_format }}.

API contract — POST /api/analyze (incl. error classification order)

Request: Authorization: Bearer <JWT>, body {productId}, where String(...).trim() must match ^\d+$.

Order: method → id → bearer → canEdit → getProduct + snapshot → categories ∥ peers (assigned category) → stats + prompt peers + fingerprint → BAML (signal: AbortSignal.timeout(45000)) + one llm-call log line → buildAnalysisRecord → objects.save (bound) → setData summary → 200 record.

Error classes are imported from @boundaryml/baml/errors (identical class objects, no native addon load).

Classification order (first match wins): 1. BamlAbortError / BamlTimeoutError → LLM_TIMEOUT (Timeout is a BamlClientHttpError subclass with status 408, so it must come first) · 2. BamlClientHttpError 400 with a guardrail marker → CONTENT_BLOCKED (amended — see Spec deviations) · 3. validation / finish-reason → LLM_INVALID_OUTPUT · 4. other BAML → LLM_UNAVAILABLE · 5. host errors and invalid payload → 401 / 403 / 404 (product stage) / HOST_ERROR · 6. anything else → INTERNAL.

Raw details are logged server-side only, as one sanitized line (amended — see Spec deviations). If setData fails after a save, the route returns 502 and the summary stays outdated until the next Re-analyze (known limitation).

Stored object, setData summary, fingerprint, needsReview, peers

Object: type analysis, id = productId, bound to {entityType: "PRODUCT", entityId: productId} on every save.

FieldShape
productId / fingerprint / analyzedAt / modelstring / 14 hex / ISO UTC / gpt-4o-mini
needsReviewboolean
description{verdict, score, summary, issues[], suggestions[]}
category{verdict, assigned {id, name}, suggested {id, name} | null, reasoning}

Summary (setData, top level only): needsReview (boolean), descriptionVerdict, categoryVerdict, priceVerdict, and priceDeviationPct (int, omitted when null). No fingerprint.

Fingerprint: cyrb53(JSON.stringify([name.trim(), description.trim(), price.toFixed(2), sku.trim(), category.id, category.name.trim()])) written as 14 hex characters, after toProductSnapshot normalization (null description becomes ""). It does not cover other categories or peer prices (known limitation).

needsReview: POOR or MISMATCH or (ABOVE/BELOW_MARKET and deviationPct ≠ null and |deviationPct| ≥ 30).

Deviation: round((price − mid)/mid·100) with mid = (min+max)/2. It is null for INSUFFICIENT_DATA, a missing bound, min ≤ 0, or max < min.

Peer stats: products of the assigned category, excluding self via String(p.id) === String(self.id) (host ids are JSON numbers), keeping finite positive prices, sorted. Gives count/min/median (mean of the two middle values for an even count)/max rounded to 2 decimals, or null when there are none.

Prompt peers (selectPromptPeers): same filter; when more than 10 remain, the 10 closest in price to the product (ties by name), listed by price ascending. Stats still use all peers.

Suggested category: case-insensitive trimmed match against /api/categories. It is null when there is no match or the match is the assigned category.

Tab (auto-run visibility gate), badge and BroadcastChannel behaviour
  • Tab load (at mount, even while hidden): getToken → canEdit, objects.list("analysis", {PRODUCT, id}), and getProduct → fingerprint. The analysis is stale when the fingerprints differ. "Loading analysis…" is shown meanwhile (amended — see Spec deviations).
  • Why a gate: the host (ProductDetailPage.tsx) mounts every plugin tab iframe on page load in a display:none panel and only toggles display when the tab is clicked.
  • Visibility gate: visible = window.innerWidth > 0 && window.innerHeight > 0. If an auto-run is due and the tab is hidden, listen for window resize; on the first visible resize, remove the listener and run. Remove it on unmount.
  • One attempt: a useRef autoRunAttempted flag blocks any further auto-run in the iframe session, success or error. After an auto-run error only Retry runs again; switching tabs never re-triggers.
  • Editor: otherwise shows the result plus Re-analyze. A useRef in-flight guard prevents double runs; Re-analyze and Retry are disabled while running.
  • Viewer: sees the result (with a stale note when out of date), or the "Not analyzed yet" card. Never sends a POST.
  • Header: subtitle "12 Nov 2026, 18:42 · gpt-4o-mini via LiteLLM" (en-GB date) only when an analysis exists; badge "Analyzing…" while running, else the shown analysis's verdict or "Not analyzed" (also in the error state).
  • Channel "ai-offer-analysis": message {type: "analysis-saved", productId, needsReview} after a 200. The badge re-reads getData when the productId matches and closes the channel on unmount.
  • Badge: "AI review: Needs review" (danger) plus reasons in fixed order (price, category, description) such as "price +46% above market · category mismatch"; "AI review: Looks good" (success); "AI review: not analyzed yet" (plain); "AI review: unavailable" when getData errors.

Testing Approach

2–8 focused tests per step group (the domain suite goes to 10 to cover the UI helpers). Verification runs only the new tests, plus a final host regression run.

domain.test.ts (≤ 10)
  1. Fingerprint is deterministic and normalizes values
  2. Fingerprint changes on each field
  3. needsReview truth table
  4. Peer stats + prompt peers: numeric host ids, self excluded, odd/even median, empty list, 10 closest kept
  5. Deviation: rounding and null cases
  6. Suggested category resolution
  7. canEdit with base64url / READ / malformed tokens
  8. Record builder narrowing + summary shape
  9. verdictBadgeClass + priceBadgeLabel (Unicode minus, 30% threshold)
  10. toAnalysisSummary (null cases) + reviewReasons (order, " · " join)
analyze.test.ts (≤ 8)
  1. 405 + Allow: POST
  2. 400 for an invalid id
  3. 403 without EDIT; no host or BAML calls
  4. Host 404 → 404; no BAML call
  5. Happy path: save arguments with binding, setData summary, assigned-category getProducts, peers exclude self (numeric ids), USD formatting
  6. Guardrail-marked HTTP 400 → 502 CONTENT_BLOCKED; no save, no raw details; sanitized log line (amended — see Spec deviations)
  7. Classification order: Abort and Timeout (408 subclass) → LLM_TIMEOUT; generic → LLM_UNAVAILABLE; non-guardrail 400 and a 400 that only says "blocked" → LLM_UNAVAILABLE (amended — see Spec deviations)
  8. Unknown suggestion → suggested: null

BAML errors are built from @boundaryml/baml/errors, the module the route imports. Host regression: ./mvnw test passes with the 013 seed (no new Java tests). UI pages (visibility gate, one-attempt rule) are covered by live and E2E verification against the mockups.

LiteLLM Verification Procedure (acceptance)

Preconditions: a real OPENAI_API_KEY in litellm/.env (now an OpenRouter key (amended — see Spec deviations)); docker compose up -d with the services healthy; the host on :8080 (dev seed applied); the plugin on :3011 with .env.

Ground truth: the [ai-offer-analysis] llm-call ... outcome=... lines in the plugin's npm run dev terminal (browser POST /api/analyze count is a cross-check). ok / LLM_INVALID_OUTPUT → exactly one entry each; LLM_TIMEOUT → 0 or 1 (aborted calls may still be logged; excluded from the equality); CONTENT_BLOCKED / LLM_UNAVAILABLE → no success entry.

  4. Langfuse at http://localhost:3100 (admin@aj.local / admin123), project "AJ Plugins": tagged traces with input and output.

  6. Fallback: if there is no tag and no end user, add the x-litellm-tags header, repeat, and document which mechanism worked.
  7. Record start time, llm-call count and outcomes, baseline and delta, tag/end-user evidence and Langfuse trace ids in the verification report.

Standards Compliance

  • plugin-development: naming and version, shared SDK imports, mandatory tc-*, manifest as source of truth, storage choice, fixed port with -p, try/catch for SDK calls.
  • plugin-auth: getToken → plugin backend → createServerSDK(id, undefined, req); JWT permissions decoded base64url-safe.
  • error-handling / validation: typed classification, sanitized messages, server-side id validation, verdict allow-lists, category validation.
  • conventions: .env from .env.example; provider keys only in litellm/.env; course folders untouched.
  • minimal-implementation: no bulk page, virtual keys, SDK fix, retry or fallback wrappers, or unused summary fields.
  • migrations: 013-insert-..., dev context, rollbacks; no schema change and no jOOQ regeneration.
  • components / css / accessibility: named functions (default export only because Next.js requires it), no hex colors, import type, verdict text with color, aria-live, labelled progress.
  • backend-testing: the host suite stays green with the seed.

Success Criteria

  • npm install && npm test passes on Windows and bash (≤ 18 tests: domain ≤ 10, route ≤ 8); npm run build succeeds.
  • ./mvnw test passes; on a fresh dev database the plugin row and demo products exist; re-running Liquibase is a no-op; a renamed/deleted demo category skips that product without breaking startup.
  • Tab, badge and "AI: needs review" switch are visible on :3011.
  • Editor: a product page visit without opening the tab makes no /api/analyze call. The first tab open for a new or changed product runs exactly one analysis. Re-opening without changes makes no LLM call. Changing name, description, price, SKU or category, or renaming the assigned category, triggers exactly one re-run on the next tab open. A failed auto-run is not repeated in the same page session.
  • Viewer: never calls /api/analyze.
  • Each demo product shows Needs review with at least its strongly cued flag (TV: POOR and/or MISMATCH; Skylink: MISMATCH); peer rows show the assigned category without the product itself. The badge refreshes without a reload, and the filter finds the flagged products.
  • Only sanitized error messages reach the browser.
  • LiteLLM: delta of tagged /spend/logs rows over the baseline equals the expected count from the llm-call lines (aborts excluded); attributed by tag or end user; unmasked USD prices in the prompt; Langfuse traces present; evidence recorded; procedure (bash + PowerShell) in the README.
  • All listed docs mention the plugin and port 3011.
